### 가격 실험 권장 범위

경쟁 사례를 바탕으로 한 첫 실험 범위이며 확정 가격은 아니다.

| 상품 | 낮은 가격안 | 기준 가격안 | 높은 가격안 | 역할 |
|---|---:|---:|---:|---|
| 3일 패스 | `$0.99` | `$1.99` | `$2.99` | 짧은 여행의 진입 상품 |
| 7일 패스 | `$1.99` | `$3.99` | `$4.99` | 중앙 추천 상품 |
| 30일 패스 | `$7.99` | `$9.99` | `$14.99` | 장기 수요 및 가격 앵커 |

첫 가격 의향 화면에서는 기준 가격안 하나를 고정하기보다 방문자를 가격안별로 나누는 실험이 더 적합하다. 실제 결제 전에는 다음 계산이 필요하다.

```text
패스당 예상 매출
- 결제 수수료
- 패스 기간의 예상 분석 횟수 × 분석 1회 원가
- 이미지·DB·로그 보관 비용
- 환불·고객지원 충당 비용
= 패스당 예상 공헌이익
```

시장 가격만 보면 3·7·30일 구조는 방어 가능하다. 다만 TransTaste가 추천할 중앙 상품은 “기간의 중앙값”이 아니라 목표 고객의 대표 여행 기간과 예상 공헌이익을 기준으로 7일 패스로 정해야 한다.


## 코드에 즉시 적용한 안전 기본값

다음 항목은 제품 방침을 기다리지 않고 안전 기본값으로 적용했다.

구체적인 코드 반영과 검증 상태는 [방침 구현 상태](./260730_policy_implementation_status.md)에서 관리한다.

- Stripe 키가 없으면 checkout API가 성공 URL을 만들지 않고 `503 E_SERVICE_UNAVAILABLE`을 반환한다.
- 결제 실패 시 로컬 패스·크레딧·상세 잠금 해제를 부여하지 않는다.
- `?payment=success` 쿼리만으로 유료 권한을 부여하지 않는다.
- 결제 기능이 준비되지 않은 동안 사용자를 실제 청구가 없는 가격 의향 검증 페이지로 보낸다.
- 메뉴 분석과 상세 분석의 데모 응답은 명시적 `ENABLE_DEMO_ANALYSIS=true` 환경에서만 허용한다.
- 여행 도구의 주문 카드는 이미 구현된 주문 화면으로 연결한다.

## 의사결정 후 필요한 구현

### Supabase를 도입하는 경우

- 사용자·익명 세션 연결 정책
- Row Level Security와 사용자별 기록 접근
- 원본 이미지 보존 여부 및 자동 삭제 작업
- 사용자 데이터 내보내기·삭제·탈퇴
- Stripe Customer와 내부 사용자 ID 연결

### Stripe를 도입하는 경우

- Checkout Session 생성 시 인증된 사용자 ID를 metadata/client reference에 기록
- webhook 서명 검증
- webhook 기반 서버 측 entitlement 생성
- 성공 페이지에서 서버 entitlement를 조회하고 클라이언트 쿼리를 신뢰하지 않음
- 중복 webhook의 idempotency
- 취소·환불·분쟁 시 entitlement 회수 정책

### 실제 AI를 공개하는 경우

- 대표 국가·메뉴·촬영 조건별 정확도 평가 세트
- 심각 알레르기 미탐률을 별도 품질 지표로 관리
- 모델·프롬프트 버전과 분석 결과 추적
- 시간 초과, rate limit, 부분 분석의 사용자 복구 흐름
- 원어민 검수된 직원 제시 문장 라이브러리
