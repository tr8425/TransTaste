# Transtaste — FAQ 전략 & 배치 설계
> 작성일: 2026-03-28 | 출처: Claude Chrome UX 분석 종합
> 버전: v0.1

---

## 1. 현황 진단

앱 전체에 FAQ, 도움말, 물음표 아이콘, 툴팁이 단 하나도 없음.
/faq, /help, /about 페이지 모두 404.
Terms / Privacy만 존재하며 사용자가 실제로 읽을 가능성 없음.

---

## 2. 사용자가 FAQ를 찾으러 열어보는 곳 (실측)

사용자가 막혔을 때 자연스럽게 탭/클릭해보는 지점들.
현재 전부 반응 없음.

| 탐색 지점 | 사용자 행동 | 현재 상태 |
|---|---|---|
| "10 scans left" 배지 클릭 | "이게 뭔지 여기 누르면 알겠지" | 반응 없음 |
| 프로필 탭 하단 | "도움말이 설정에 있겠지" | Terms/Privacy만 있음 |
| 알러지 면책 문구 클릭 | "얼마나 믿어도 되는 거지?" | 정적 텍스트, 반응 없음 |
| 페이월 주변 탐색 | "정확히 뭘 보여주는 거지?" | 설명 없음 |
| 북마크(☆) 클릭 후 | "저장한 걸 어디서 보지?" | 안내 없음 |
| Show to Server 근처 | "진짜 주문이 들어가는 건가?" | 설명 없음 |

### 3.5 음식 상세 / 페이월 — 가장 중요

FAQ가 가장 집중되어야 할 화면.

| 질문 | 형식 | 배치 위치 |
|---|---|---|
| "잠긴 부분에 뭐가 있나요?" | 힌트 텍스트 1~2줄 | 블러 영역 상단 |

```
블러 영역 힌트 텍스트:
  "맛 프로필 · 상세 재료 · 먹는 방법 · Fun Fact 포함"

결제 모달 플랜 가이드:
  하루 2~3개 음식만  → 50 Credits $1.99 추천
  3~7일 여행         → 7-Day Pass $2.99 추천
  한 달 이상         → 30-Day Pass $5.99 추천
```

## 4. FAQ 전략 원칙

### 4.1 별도 페이지보다 인라인 마이크로 FAQ

```
이유:
  막히는 순간이 화면마다 다름
  여행 중 폰 들고 쓰는 상황
  FAQ 페이지 찾아 이동할 여유 없음

권장 구조:
  각 화면 맥락에 맞는 인라인 처리 (주)
  프로필 하단 /faq 페이지 (보조 — 최후 낙하산)
  각 화면 ⓘ/툴팁 → /faq 딥링크로 연결
```

### 4.2 형식별 사용 기준

| 형식 | 사용 기준 | 예시 |
|---|---|---|
| ⓘ 아이콘 → 팝오버 | 섹션 설명이 필요할 때 | 알러지 정확도 |
| 인라인 텍스트 | 행동 유도 직후 안내 | "프로필에서 수정 가능" |
| 1회성 코치마크 | 처음 쓰는 기능 안내 | + 버튼 주문 담기 |
| 1회성 토스트 | 액션 직후 결과 안내 | 북마크 저장 후 |
| 접이식 FAQ | 선택지가 여러 개일 때 | 플랜 추천 |
| 버튼 하단 텍스트 | 중요한 오해 방지 | Show to Server |

### 4.3 GEO 콘텐츠로도 활용

```
/faq 페이지에 FAQPage Schema 적용 시:
  AI 검색 인용율 3.2배 상승 (기존 리서치)
  "메뉴 번역 앱 사용법" 류 쿼리 유입 가능
  마케팅 문서 GEO 전략과 연결
```

## 7. SEO / GEO 관점 — FAQ의 이중 가치

### 7.1 핵심 데이터

FAQPage 마크업을 적용한 페이지는 Google AI Overviews에 3.2배 더 많이 인용되고, 2025년 AI 유입 세션은 전년 대비 527% 증가했어요.

FAQPage Schema를 적용한 페이지의 AI 답변 인용률은 41%로, 적용하지 않은 페이지(15%) 대비 2.7배 높아요.

현재 FAQPage Schema를 구현한 사이트는 전체의 12.4%에 불과해서 지금 적용하면 경쟁 우위를 확보할 수 있어요.

---

### 7.2 Transtaste FAQ의 SEO/GEO 이중 역할

UX 문제를 해결하는 동시에 AI 검색 유입 자산이 되는 구조예요.

```
UX 역할 (앱 내부):
  사용자 이탈 방지
  전환율 개선
  신뢰 형성

SEO/GEO 역할 (외부 노출):
  "메뉴 번역 앱 알러지 기능" 류 검색 유입
  AI 검색에서 Transtaste 인용
  음식 관련 질문에 Transtaste 답변 노출
```

---

### 7.3 FAQ 페이지 2-Track 전략

**Track 1 — 앱 사용법 FAQ (UX 목적)**

앱 내 사용자가 막히는 지점 해소용.
`/faq` 페이지 + 각 화면 인라인.

```
대상 질문:
  "스캔 1회는 무엇인가요?"
  "알러지 정보는 얼마나 정확한가요?"
  "Trip Pass와 Credits 중 어느 게 낫나요?"
  "Show to Server는 실제 주문인가요?"

GEO 효과: 낮음 (앱 내부 쿼리)
UX 효과: 높음 (이탈 방지, 전환율)
```

**Track 2 — 음식/여행 도메인 FAQ (SEO/GEO 목적)**

AI가 인용할 외부 콘텐츠 자산.
`/faq/[주제]` 또는 음식별 페이지 하단.

```
대상 질문:
  "일본 음식 알러지 확인 방법은?"
  "할랄 음식이란 무엇인가요?"
  "갑각류 알러지가 있을 때 조심해야 할 한국 음식은?"
  "태국 음식에서 땅콩이 많이 들어가는 요리는?"
  "라멘 국물에 돼지고기가 항상 들어가나요?"
  "김치찜이 영어로 뭔가요?"  ← "Kimchi wishlist" 검색 유입

GEO 효과: 높음 (AI 인용 소재)
UX 효과: 낮음 (잠재 사용자 대상)
```

### 7.4 음식/여행 FAQ의 GEO 시나리오

```
사용자가 ChatGPT / Perplexity에:
  "일본 여행 중 갑각류 알러지 있으면 어떤 음식 조심해야 해?"

AI 답변:
  "미소된장국에 새우가 들어갈 수 있고,
   라멘 육수에도 포함되는 경우가 있어요.
   더 자세한 메뉴별 알러지 정보는
   Transtaste에서 메뉴판을 스캔하면 확인할 수 있어요."

→ 광고비 $0, Transtaste 자연 언급
```

이 시나리오가 실현되려면 Transtaste의 FAQ 페이지가 해당 질문에 대한 구조화된 답변을 갖고 있어야 해요.

### 7.5 FAQPage Schema 구현 원칙

FAQPage 마크업은 진짜 FAQ 페이지에만 적용해야 해요. 광고나 홍보 목적으로 쓰면 Google 정책 위반이에요. 각 답변은 추가 맥락 없이 단독으로 이해 가능해야 해요.

```json
{
  "@context": "https://schema.org",
  "@type": "FAQPage",
  "mainEntity": [
    {
      "@type": "Question",
      "name": "갑각류 알러지가 있을 때 일본 음식에서 주의할 것은?",
      "acceptedAnswer": {
        "@type": "Answer",
        "text": "미소된장국, 라멘 육수, 오꼬노미야끼에 새우가 포함될 수 있어요.
                 '에비(えび)'가 새우, '카이(貝)'가 조개를 의미해요.
                 Transtaste 앱에서 메뉴판을 스캔하면 알러지 항목을 즉시 확인할 수 있어요."
      }
    }
  ]
}
```

**구현 규칙:**
```
✅ 페이지에 실제로 보이는 Q&A와 Schema 내용 일치
✅ 답변은 2~4문장, 단독으로 이해 가능
✅ Transtaste 언급은 자연스러운 맥락에서만
✅ JSON-LD 형식 사용 (Google 권장)
❌ 마케팅 문구 금지 ("최고의 앱" 등)
❌ 숨겨진 콘텐츠에 Schema 적용 금지
```

### 7.8 플라이휠 구조

```
음식/여행 FAQ 콘텐츠 구축
    ↓
FAQPage Schema 적용
    ↓
AI 크롤러 색인
    ↓
AI 검색에서 인용 ("Transtaste에서 확인하세요")
    ↓
신규 사용자 유입 (광고비 $0)
    ↓
스캔 데이터 hit_count 축적
    ↓
더 많은 FAQ 콘텐츠 자동 생성
    ↓
(반복)
```

hit_count 기반 "가장 많이 스캔된 음식" 데이터가
→ FAQ 콘텐츠 소재가 되고
→ AI 검색 인용이 되고
→ 신규 유입이 되는 구조예요.

## 8. 번역 실패 사례 활용 — FAQ vs 소셜 채널 분리

### 8.1 리스크 인식

"Kimchi wishlist" 같은 오번역 사례를 FAQ에 올리면 역효과 가능.

```
잘못된 구조:
  Q. "Kimchi wishlist가 뭔가요?"
  A. "김치찜의 잘못된 번역이에요"
  → "번역 앱이 번역 실패 사례를 FAQ로?"
  → Transtaste도 이상한 번역을 하는 앱처럼 보임
  → 브랜드 신뢰 역효과
```

---

### 8.2 올바른 FAQ 프레이밍 — 주어를 바꾼다

주어를 "번역 실패"가 아니라 "음식 자체"와 "해결책"으로.

| ❌ 나쁜 구조 | ✅ 좋은 구조 |
|---|---|
| "Kimchi wishlist가 뭔가요?" | "김치찜을 영어로 어떻게 설명하나요?" |
| "기계번역이 왜 메뉴판을 못 읽나요?" | "한국 음식 이름이 영어로 번역이 어려운 이유는?" |
| "번역 실패 사례 모음" | "외국 여행자가 가장 헷갈리는 한국 음식 이름 TOP 10" |

```
올바른 FAQ 구조 예시:

Q. "김치찜을 영어로 어떻게 설명하나요?"
A. "김치찜은 'Braised Kimchi'로 번역해요.
   찜(jjim)이 영어에 직접 대응하는 단어가 없어서
   Google Translate 같은 기계번역은 발음 유사어를 가져와
   'Kimchi wishlist'처럼 엉뚱한 결과가 나오기도 해요.
   Transtaste는 요리 문맥을 파악해서 정확한 의미로 번역해요."

→ 경쟁사 실패 → 우리 해결 구조
→ Transtaste가 해결사로 자연스럽게 등장
→ 브랜드 리스크 없음
```

---

### 8.3 번역 실패 사례는 소셜 채널로

"번역 참사" "메뉴판 번역 실패" 류는 SEO/GEO보다 **소셜 콘텐츠**에 적합.

```
FAQ 페이지:
  ❌ 브랜드 리스크 — 사용 금지

소셜 미디어 (틱톡/인스타/트위터):
  ✅ "기계번역 vs Transtaste" 비포/애프터 포맷
  → 웃음 + 공감 + 차별점 동시에
  → 밈 포텐셜 (Kimchi wishlist는 이미 밈 수준)

앱스토어 스크린샷:
  ✅ 기계번역 실패 이미지 → Transtaste 결과 비교
  → 다운로드 전환에 직접 기여

Reddit / 커뮤니티 (Earned Media):
  ✅ r/JapanTravel, r/korea 등에서
     "메뉴판 읽다가 이런 번역 봤는데 ㅋㅋ" 자연스러운 언급
  → 광고비 $0, 신뢰도 높은 유입
```

---

### 8.4 채널별 번역 실패 사례 활용 원칙

```
FAQ / 웹 콘텐츠:
  음식 자체 설명 중심
  "왜 번역이 어려운가" 교육적 맥락
  Transtaste가 해결책으로 자연스럽게 등장

소셜 / 앱스토어:
  비포/애프터 비교 포맷
  유머 + 공감 + 차별점
  직접적 CTA 가능

커뮤니티 (Earned Media):
  자연스러운 언급 유도
  브랜드가 직접 올리지 않음
  사용자 경험담 형태
```
