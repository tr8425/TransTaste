# TransTaste Codex 디자인·플로우 수정 계획

> 작성일: 2026-07-30
> 목표: Supabase·Stripe 투자 전에 핵심 상품 가설을 2주 안에 검증할 수 있는 제품으로 개편
> 관련 문서: `Docs/260730_product_viability_review.md`

## 1. 작업 원칙

1. 범용 메뉴 번역보다 “제한식 사용자의 메뉴 선택과 현지어 주문”을 전면에 둔다.
2. 회원가입·결제·서버 크레딧 구현은 검증 지표 통과 전까지 보류한다.
3. 기존 Next.js/PWA 구조와 로컬 데이터 구조를 유지한다.
4. 첫 스캔 성공까지 필요한 선택을 최소화한다.
5. 결과 화면에서 정보량보다 결정과 행동을 우선한다.
6. AI 안전 보장을 암시하지 않는다.
7. 각 단계는 Codex가 독립적으로 구현하고 검증할 수 있는 크기로 나눈다.

## 2. 목표 사용자 플로우

### 신규 사용자

```text
홈
  ├─ 메뉴 촬영
  ├─ 갤러리 선택
  └─ 샘플로 체험
       ↓
간단 제한식 선택
  - 없음
  - 채식/비건
  - 할랄
  - 피해야 할 재료
       ↓
분석 화면
  - 진행 상황
  - 첫 요리부터 순차 표시
       ↓
결과
  - 먼저 볼 것: 피하기 / 확인 필요 / 선택 가능
  - 요리 선택
  - 주문에 추가
       ↓
점원에게 보여주기
  - 원문 주문
  - 제한식 문장
  - 큰 글자, 고대비, 화면 유지
       ↓
설정 저장 제안
```

### 재방문 사용자

```text
홈
  → 즉시 촬영
  → 저장된 제한식 적용 여부 확인
  → 결과
  → 이전 기록 또는 새 주문
```

## 3. 정보 구조 개편

### 홈 `/`

현재 홈의 역할을 하나로 줄인다.

> 사용자가 5초 안에 메뉴 촬영 또는 샘플 체험을 시작하게 한다.

#### 상단

- 브랜드 로고
- 짧은 가치 문구
- 대표 CTA `메뉴 스캔하기`
- 보조 CTA `샘플로 먼저 보기`
- 갤러리/URL/텍스트는 `다른 입력 방법` 아래로 축소

#### 가치 증명

- 실제 메뉴 이미지
- 변환된 결과 카드 3종
- “피해야 함 / 직원 확인 / 선택 가능” 예시
- 점원 표시 화면 미리보기

#### 신뢰

- 감지 가능한 제한식 종류
- 지원 언어
- “AI 참고 정보이며 직원 확인 필요” 고지

#### 하단

- 회화, 팁 문화, 음식 가이드는 `여행 도구` 섹션으로 이동
- Popular Dishes는 SEO 진입 경로로 유지하되 핵심 CTA보다 아래 배치

### 온보딩 `/onboarding`

기존 다중 슬라이드를 첫 진입 필수 플로우에서 제거한다.

- 홈에서 자동 리다이렉트하지 않는다.
- 스캔 직전 또는 분석 중 제한식만 간단히 묻는다.
- 언어와 통화는 브라우저 기본값을 사용한다.
- 상세 알레르기·통화 설정은 결과 이후 프로필에서 제안한다.
- 기존 온보딩 페이지는 설정 마법사 또는 소개 페이지로 재사용한다.

### 카메라 `/camera`

- 촬영 프레임과 셔터를 최우선으로 유지
- 여러 장 촬영 가능 여부를 명확히 표시
- 저조도·반사·흔들림 촬영 팁을 한 줄로 제공
- 촬영 후 즉시 분석으로 보내기 전에 미리보기와 재촬영 제공
- 권한 거부 시 갤러리 업로드 CTA를 기본 대안으로 제공

### 분석 `/loading-scan`

- 로딩 애니메이션보다 진행 상태를 신뢰감 있게 표현
- `메뉴 읽는 중 → 요리 분류 중 → 제한식 확인 중`
- 첫 요리가 준비되면 전체 완료를 기다리지 않고 표시
- 15초 이상이면 사진 품질과 네트워크 상태 안내
- 실패 시 텍스트 입력 또는 재촬영으로 바로 전환

### 결과 `/results`

결과 화면의 첫 질문은 “무엇을 먹을 수 있는가?”다.

#### 상단 요약

- 메뉴 언어·국가
- 요리 수
- 제한식 기준
- 위험 요리 수
- 직원 확인 필요 수

#### 기본 정렬

1. 제한에 비교적 적합
2. 직원 확인 필요
3. 피하는 것이 좋음

#### 필터

- 전체
- 선택 가능
- 직원 확인
- 피하기
- 채식/할랄 등 현재 사용자 제한식

#### 카드 축약 정보

- 원문명
- 사용자 언어 요리명
- 한 줄 설명
- 가격과 환산 가격
- 제한식 상태
- 선택 이유 또는 위험 이유
- `주문에 추가`
- `자세히`

상세 맛 프로필, 칼로리, 문화 정보는 BottomSheet로 이동한다.

#### 안전 문구

- `안전함` 대신 `현재 메뉴에서 명시된 위험 없음`
- 모든 상태에 근거를 노출
- `직원에게 확인하기` CTA 제공

### 주문 `/order`

- 선택한 요리, 수량, 가격을 우선
- 원문명과 번역명을 항상 병기
- 제한식 위험이 있는 항목을 다시 경고
- 대표 CTA를 `점원에게 보여주기`로 변경

### 점원 표시 `/order/present`

- 앱의 대표 차별 기능으로 승격
- 원문 주문을 가장 크게 표시
- 사용자 제한식 문장을 현지어로 함께 표시
- 화면 밝기 유지와 Wake Lock 유지
- 세로 화면에서 스크롤을 최소화
- 음식별 옵션과 제외 요청 표현
- “이 내용이 맞나요?” 확인 문구 포함

### 프로필 `/profile`

- 개발자 API 키 입력은 일반 사용자 화면에서 제거하거나 개발 모드로 제한
- 설정을 다음 순서로 재배치
  1. 언어
  2. 통화
  3. 제한식
  4. 피하는 재료
  5. 데이터 삭제
- 크레딧·결제 UI는 검증 단계에서 `가격 보기` 실험으로만 유지

## 4. 디자인 시스템 방향

### 유지

- 크림 배경
- 코랄 포인트
- 브라운 텍스트
- 둥근 카드와 모바일 우선 레이아웃
- Geist 폰트

### 변경

- 기능 이모지를 일관된 SVG 아이콘으로 교체
- 위험 상태를 색상 + 아이콘 + 텍스트로 표시
- 버튼 위계를 primary / secondary / tertiary로 제한
- 카드 내부 정보 밀도를 줄이고 행동 버튼을 분명히 표시
- 실제 메뉴·요리·점원 표시 화면을 대표 비주얼로 사용

### 상태 토큰

| 상태 | 색상 방향 | 아이콘 | 표현 |
|---|---|---|---|
| 피하기 | danger/red | 경고 삼각형 | 포함 가능성 높음 |
| 직원 확인 | amber | 질문/대화 | 조리법 확인 필요 |
| 명시 위험 없음 | green | 정보 체크 | 안전 보장 아님 |
| 정보 부족 | neutral | 정보 | 분석 정보 부족 |

색상 이름과 실제 Tailwind 토큰은 기존 `tailwind.config.ts`를 기반으로 정리한다.

## 5. 측정 설계

Supabase 없이도 초기에는 익명 이벤트 수집 도구 또는 Vercel Web Analytics를 사용할 수 있다. 도구 선택은 별도 승인 후 진행한다.

### 최소 이벤트

| 이벤트 | 시점 |
|---|---|
| `home_view` | 홈 진입 |
| `scan_cta_click` | 카메라·갤러리·샘플 시작 |
| `dietary_quick_select` | 간단 제한식 선택 |
| `analysis_started` | API 요청 시작 |
| `analysis_first_result` | 첫 요리 표시 |
| `analysis_completed` | 전체 결과 완료 |
| `analysis_failed` | 실패 코드와 입력 방식 |
| `dish_opened` | 상세 열기 |
| `dish_added_to_order` | 주문 추가 |
| `present_mode_opened` | 점원 표시 진입 |
| `pricing_viewed` | 가격 UI 표시 |
| `purchase_intent_clicked` | 결제 CTA 클릭 |

### 필수 속성

- 입력 방식
- 메뉴 언어
- 사용자 출력 언어
- 제한식 유형
- 메뉴 항목 수
- 첫 결과 소요 시간
- 전체 완료 소요 시간
- 성공/실패 코드

이미지, 메뉴 원문, API 키 등 민감 정보는 이벤트에 포함하지 않는다.

## 6. Codex 실행 단계

### Phase 0 — 기준선과 안전장치

목표: 변경 전 동작과 검증 방법을 고정한다.

작업:

- 주요 플로우의 현재 스크린샷 확보
- 모바일 390×844 기준 QA
- 홈 → 카메라 → 로딩 → 결과 → 주문 → 점원 표시 시나리오 기록
- i18n, lint, build 기준선 실행
- 현재 localStorage/sessionStorage 계약 문서화
- mock 모드가 프로덕션 결제처럼 보이지 않도록 상태 구분안 작성

완료 기준:

- 기준 스크린샷과 QA 체크리스트 존재
- `npm run lint`, `npm run check:i18n`, `npm run build` 통과

### Phase 1 — 홈과 첫 진입 개편

대상:

- `src/app/page.tsx`
- `src/app/onboarding/page.tsx`
- `src/components/common/*`
- `src/lib/i18n/*.json`

작업:

- 필수 온보딩 리다이렉트 제거
- 핵심 가치 문구 교체
- 대표 CTA와 샘플 체험 추가
- 다른 입력 방식 축소
- 실제 결과 예시 섹션 추가
- 안전 고지와 신뢰 정보 추가

완료 기준:

- 신규 사용자가 홈에서 한 번의 주요 클릭으로 체험 시작
- CTA가 모바일 첫 화면에 표시
- 온보딩 없이 샘플 결과 도달 가능

### Phase 2 — 제한식 빠른 선택

대상:

- 신규 `src/components/onboarding/QuickDietarySetup.tsx`
- `src/app/camera/page.tsx`
- `src/app/loading-scan/page.tsx`
- 사용자 설정 로컬 저장 로직

작업:

- 없음/채식/비건/할랄/피해야 할 재료 빠른 선택
- 상세 알레르기 설정은 선택 사항으로 분리
- 기존 설정이 있으면 재사용 여부만 확인
- 분석 요청에 빠른 설정 반영

완료 기준:

- 빠른 선택이 20초 이내 완료
- 건너뛰기 가능
- 기존 설정과 충돌하지 않음

### Phase 3 — 결과 의사결정 UI

대상:

- `src/app/results/page.tsx`
- `src/components/dish/DishRow.tsx`
- `src/components/dish/DishCard.tsx`
- `src/components/common/LowConfidenceBanner.tsx`
- `src/lib/types.ts`

작업:

- 제한식 상태 중심 요약
- 상태 기준 정렬과 필터
- 카드 정보 축약
- 위험 근거 노출
- `직원에게 확인` CTA
- `safe` 표현 제거

완료 기준:

- 사용자가 상세를 열지 않고도 요리 후보를 고를 수 있음
- 색상을 보지 않아도 상태를 이해할 수 있음
- 불확실한 결과에 직원 확인 경로가 있음

### Phase 4 — 주문과 점원 표시 강화

대상:

- `src/app/order/page.tsx`
- `src/app/order/present/page.tsx`
- `src/hooks/useCart.ts`
- `src/lib/allergen-i18n.ts`

작업:

- 원문과 번역 병기
- 제한식 재확인
- 점원 표시 CTA 강화
- 요청 문장과 주문 항목을 한 화면에 구성
- 큰 글자·고대비·Wake Lock 검증

완료 기준:

- 점원이 화면만 보고 주문 항목과 제한 사항을 이해 가능
- 390×844에서 핵심 내용이 과도한 스크롤 없이 표시

### Phase 5 — 측정과 가격 의향 실험

선행 조건:

- 이벤트 도구 선택 승인
- 개인정보 처리 문구 검토

작업:

- 최소 이벤트 구현
- 가격 보기 UI
- 결제 CTA는 실제 결제 대신 관심 등록 또는 “출시 알림” 처리
- 실험 가격안 A/B 또는 순차 테스트
- 지표 대시보드 정의

완료 기준:

- 핵심 퍼널 수집
- 결제 없이 가격 CTA 클릭률 측정
- 민감 데이터 미수집

### Phase 6 — 사용자 검증

작업:

- 제한식 해외여행자 10~20명 모집
- 실제 메뉴 3종 과제
- Lens 또는 ChatGPT와 비교
- 주문 결정 시간 측정
- 점원 표시 이해도 평가
- 결제 의향 인터뷰

완료 기준:

- 상품성 문서의 투자 게이트 지표 산출
- Go / Pivot / Stop 결정

## 7. Codex 작업 단위와 검증 규칙

각 Phase는 별도 브랜치 또는 별도 커밋 단위로 진행한다.

Codex 작업 요청 형식:

```text
Docs/260730_codex_design_flow_plan.md의 Phase N을 구현해줘.
현재 사용자 변경을 보존하고, 대상 파일 범위를 우선 지켜줘.
구현 후 lint, i18n, production build를 실행하고
390×844 모바일 기준 핵심 플로우를 브라우저로 검증해줘.
범위 밖의 Supabase, Stripe, 결제, 인증은 구현하지 마.
```

단계별 공통 검증:

```powershell
$env:NODE_OPTIONS='--use-system-ca'
npm run lint
npm run check:i18n
npm run build
```

브라우저 검증:

- `/`
- `/camera`
- `/loading-scan`
- `/results`
- `/order`
- `/order/present`
- `/profile`

확인 항목:

- 390×844 레이아웃
- 키보드 탐색
- 버튼 접근 가능한 이름
- 색상 외 상태 표현
- 한국어/영어
- 브라우저 저장소가 비어 있는 신규 사용자
- 기존 설정이 있는 재방문 사용자
- 카메라 권한 거부
- API 실패와 타임아웃

## 8. 변경하지 않을 범위

검증 전에는 다음을 구현하지 않는다.

- Supabase Auth
- 서버 사용자 프로필
- Stripe Checkout/Webhook
- 서버 크레딧 원장
- 네이티브 앱
- B2B 식당 관리 기능
- 그룹 주문 백엔드
- 대규모 음식 데이터 추가
- 전체 Next.js 메이저 업그레이드

보안 취약점 대응을 위한 프레임워크 업그레이드는 상품 검증 작업과 별도 작업으로 계획한다.

## 9. 의사결정

Phase 6 종료 후 다음 기준으로 결정한다.

### Go

- 핵심 퍼널 기준 통과
- 제한식 사용자가 무료 대체재보다 선호
- 가격 CTA 클릭과 결제 의향 확인

다음 투자:

- Supabase Auth와 서버 크레딧
- Stripe 결제
- AI 품질 벤치마크 확대
- 네이티브 앱 검토

### Pivot

- 스캔 사용은 있으나 결제 의향이 낮음
- 점원 표시나 회화 기능만 강한 반응

가능한 전환:

- 무료 메뉴 분석 + 유료 여행 주문 도우미
- 제한식 카드와 현지어 주문에 집중
- 여행사·숙박 제휴

### Stop

- 첫 스캔 시작률과 결과 행동이 모두 낮음
- 무료 대체재 대비 명확한 선호가 없음
- 두 번의 포지셔닝 실험에서 결제 의향 미확인

이 경우 현재 제품은 공개 데모와 포트폴리오로 유지하고 추가 인프라 투자를 중단한다.
