## 1. QR 메뉴 대응 전략

### 1.1 현황 및 한계

QR 코드만 있는 메뉴판을 찍으면 현재 플로우에서는 `not_menu` 에러 반환.
QR 내부 URL이 가리키는 대상이 무엇이냐에 따라 처리 가능 여부가 달라짐.

### 1.2 처리 가능 여부 (대상별)

| QR 내용 | 처리 가능 여부 | 방법 |
|---|---|---|
| 이미지 URL (.jpg/.png) | ✅ 가능 | 기존 URL 입력 파이프라인 |
| PDF 메뉴 | ✅ 가능 | Claude PDF 지원 |
| 일반 웹페이지 메뉴 | ⚠️ 불안정 | HTML 파싱 시도 — 사이트마다 구조 달라 실패 多 |
| 앱 딥링크 (예: 배민) | ❌ 불가 | 앱 접근 불가 |
| 로그인 필요 페이지 | ❌ 불가 | 인증 불가 |

### 1.3 구현 방안 (V2)

```
QR 이미지 촬영
    │
    ├─ jsQR (클라이언트 사이드) → URL 추출 성공
    │       ↓
    │   URL 타입 판별
    │   ├─ .jpg/.png/.pdf → 기존 URL 파이프라인
    │   └─ HTML 페이지 → web_fetch 시도 → 텍스트 파싱 → Claude 분석
    │
    └─ URL 추출 실패 or 지원 안 되는 타입
            ↓
        "QR 메뉴인가요? URL을 직접 입력해주세요" 안내
```

jsQR은 클라이언트 번들 (~50KB) — 추가 API 비용 없음.
크레딧 차감은 Claude 분석 성공 시에만.

### 1.4 사용자 안내 문구

```
QR 코드를 인식했어요.
메뉴 페이지를 불러오고 있어요... (웹 fetch 시도)

→ 성공 시: 기존 결과 화면
→ 실패 시: "이 QR 메뉴는 직접 열어야 해요.
            URL을 복사해서 붙여넣기 하거나
            메뉴 화면을 캡처해서 올려주세요."
```

## 2. 비정형 메뉴 / 개별 상품 사진 지원

### 2.1 대상 케이스

```
빵집       진열된 개별 빵마다 이름표
과일가게   가격표 칠판, 개별 상품 라벨
노점       손글씨 메뉴판, 실물 전시
뷔페       음식별 명패 다수
편의점     진열 상품 다수
```

### 2.2 기술적 지원 가능 여부

Claude Vision API는 요청당 최대 100장 이미지 지원.
단일 이미지, 다중 이미지, 파노라마 모두 분석 가능.

| 촬영 방식 | 처리 | 품질 | 비고 |
|---|---|---|---|
| 개별 상품 1장씩 | ✅ 높음 | 최고 | Reverse Food Search와 동일 |
| 갤러리 다중 선택 (2~10장) | ✅ 가능 | 높음 | API 1회 호출, 묶어서 처리 |
| 파노라마 와이드샷 | ✅ 가능 | 중간 | 가격표 글씨 작으면 low_confidence |
| 50+ 조밀 진열 와이드샷 | ⚠️ 불안정 | 낮음 | 개별 촬영 권장 안내 |

파노라마 인식 조건:
- 장축 1024px 이상
- 상품당 최소 50×50px 이상 차지해야 신뢰 가능
- 글씨가 너무 작으면 low_confidence 처리

### 2.3 수익 구조 영향

```
일반 식당 (메뉴판 1장)  → 1회 스캔 = 1 크레딧
빵집 / 노점             → 5~15회 스캔 = 5~15 크레딧
```

크레딧 소진이 빠르면 Trip Pass 전환 압력이 자연스럽게 높아짐.
"오늘 노점 5곳 돌아다녔더니 크레딧 다 썼어요" → 패스 구매 유도.

단, 다중 이미지를 1회 호출로 묶어 처리하면:
- 사용자: 5장 올려도 크레딧 1 소비 (편의)
- 서버: API 1회 호출 (비용 효율)
- 수익: 크레딧 소비 줄어드나 UX 만족으로 전환율 상승 기대

**결론: 다중 이미지는 API 1회 호출 / 크레딧 1회 차감으로 처리 권장.**

### 2.4 UX 설계

```
홈 화면 갤러리 버튼
    → 다중 선택 허용 (최대 10장)
    → 선택한 이미지 프리뷰 그리드 표시
    → "X개 상품 분석하기" CTA
    → 결과: 각 이미지별 카드 생성
```

파노라마 전용 모드는 별도 구현 불필요.
기존 카메라 촬영 시 가로로 찍으면 그대로 처리됨.

## 3. 캐싱 구조 상세 설계

### 3.1 4-Layer 아키텍처

```
요청
 │
 ▼
[L1] Redis 정확 매칭 캐시
     키: SHA256(정규화 입력 + 소스언어 + 타겟언어)
     TTL: 30일 / hit_count 증가
     예상 히트율: 55~60%
 │ Miss
 ▼
[L2] Redis 정규화 매칭 캐시 (신규)
     공백 제거 + 소문자 변환 + 특수문자 제거
     "불고기  " = "불고기" = "Bulgogi"
     예상 추가 히트율: +10~15%
 │ Miss
 ▼
[L3] Claude Prompt Caching (신규)
     시스템 프롬프트 고정 구간 캐시
     TTL: 5분 (동일 프롬프트 재사용 시 자동 연장)
     비용: 읽기 = 표준의 10% (90% 절감)
 │ (항상 통과)
 ▼
[L4] Claude API 호출
     신규 분석 → 결과를 L1 저장
```

### 3.2 캐시 키 생성 로직

```typescript
// src/lib/cache.ts

function normalizeDishName(name: string): string {
  return name
    .toLowerCase()
    .replace(/\s+/g, '')                    // 공백 전부 제거
    .replace(/[^\w\u3040-\u9fff\uAC00-\uD7A3]/g, '') // 특수문자 제거, 한중일 유지
    .trim()
}

function buildCacheKey(params: {
  input: string
  inputType: 'image' | 'url' | 'text'
  srcLang: string
  tgtLang: string
}): string {
  const normalized = params.inputType === 'text'
    ? normalizeDishName(params.input)
    : params.input  // 이미지·URL은 원본 해시

  return createHash('sha256')
    .update(`${params.inputType}:${normalized}:${params.srcLang}:${params.tgtLang}`)
    .digest('hex')
}
```

### 3.3 Claude Prompt Caching 구현

```typescript
// src/lib/claude.ts

const SYSTEM_PROMPT = `You are a world-class food expert...`
// 고정된 분석 규칙 전체 (~800 tokens)

export async function analyzeMenu(input: MenuInput) {
  return client.messages.create({
    model: 'claude-sonnet-4-5',
    max_tokens: 2048,
    system: [
      {
        type: 'text',
        text: SYSTEM_PROMPT,
        cache_control: { type: 'ephemeral' }  // 코드 1줄 추가
        // 5분 TTL, cache read = 표준 비용의 10%
      }
    ],
    messages: [{ role: 'user', content: buildUserContent(input) }]
  })
}
```

### 3.4 입력 타입별 모델 라우팅

```typescript
// src/app/api/analyze/route.ts

const MODEL_ROUTER = {
  text:  'claude-haiku-4-5',    // OCR 불필요, 60% 저렴
  image: 'claude-sonnet-4-5',  // Vision 필요
  url:   'claude-sonnet-4-5',  // 이미지 fetch 포함
} as const

export async function POST(req: Request) {
  const { input, inputType, userId } = await req.json()

  // 1. 크레딧 사전 확인 (차감 전)
  if (!await checkCredit(userId)) return paywallResponse()

  // 2. 캐시 조회
  const key = buildCacheKey({ input, inputType, srcLang, tgtLang })
  const cached = await redis.get(key)
  if (cached) {
    await redis.zincrby('popular:global', 1, key) // hit_count 증가
    return Response.json(JSON.parse(cached))
    // 캐시 히트 시 크레딧 차감 없음
  }

  // 3. Claude 호출 (모델 라우팅)
  const model = MODEL_ROUTER[inputType]
  const result = await analyzeMenu({ input, inputType, model })

  // 4. 결과 검증
  if (result.error === 'not_menu') {
    return errorResponse('not_menu')  // 크레딧 차감 없음
  }

  // 5. 유효한 결과만 크레딧 차감 + 캐시 저장
  await Promise.all([
    deductCredit(userId),
    redis.setex(key, 30 * 24 * 60 * 60, JSON.stringify(result)),
  ])

  return Response.json(result)
}
```

### 3.5 크레딧 차감 정책

| 상황 | 크레딧 | 이유 |
|---|---|---|
| 캐시 히트 | 0 | 서버 비용 사실상 0 |
| not_menu / ocr_failed | 0 | 사용자 실수, 트롤 억제는 무료 10회로 커버 |
| 유효한 신규 분석 | 1 | 정상 차감 |
| low_confidence | 1 | 분석 완료, 결과는 표시됨 |
| QR 디코딩 성공 + 분석 성공 | 1 | 동일 |

### 3.6 Popular Dishes 활용 (hit_count)

```typescript
// src/lib/popular.ts

// 상위 20개 조회 (Popular Dishes Nearby 섹션용)
export async function getPopularDishes(country?: string): Promise<string[]> {
  const key = country ? `popular:${country}` : 'popular:global'
  return redis.zrevrange(key, 0, 19) // 상위 20개
}

// 분석 결과 저장 시 국가별 집계도 함께
export async function recordScan(dishHash: string, country: string) {
  await Promise.all([
    redis.zincrby('popular:global', 1, dishHash),
    redis.zincrby(`popular:${country}`, 1, dishHash),
  ])
}
```

## 5. 메뉴판 트렌드 인사이트 → 서비스 영향

리서치에서 파악된 트렌드별 Transtaste 영향.

| 트렌드 | Transtaste 영향 |
|---|---|
| QR/디지털 메뉴 폭증 | OCR 대상이 화면·태블릿으로 확대. 화면 메뉴 스캔 품질 별도 테스트 필요 |
| 식물성·글로벌 퓨전 급증 | vegan 태그 정확도, 퓨전 음식 설명 품질이 더 중요 |
| 고객 메뉴 읽기 평균 109초 | 앱 결과 화면도 동일 원칙 — 중요 정보를 상단 배치 |
| LTO(한정 특선) 52% 증가 | "오늘만 있는 메뉴" 감지 → Fun Fact에 연결 가능 |
| 손그림 메뉴 트렌드 증가 | 아트 메뉴판 OCR 실패 케이스 증가 예측 → low_confidence 처리 중요 |
| 알러지 필터 메뉴판 증가 | 기존 알러지 태그 방향과 일치. 메뉴판 자체에 알러지 표기 시 직접 파싱 가능 |

## 7. 키오스크 메뉴 대응

### 7.1 결론 요약

별도 기능 개발 불필요. 기존 Vision 파이프라인 + 프롬프트 규칙 추가로 대응 가능.

### 7.2 키오스크 유형별 Transtaste 필요성

| 유형 | 다국어 지원 | Transtaste 필요 | 이유 |
|---|---|---|---|
| 글로벌 체인 (맥도날드, KFC 등) | ✅ 충분 | 불필요 | 탭 한 번으로 언어 전환 |
| 현지 유명 식당 키오스크 | ⚠️ 1~2개 언어 | 필요 | 영어 없는 경우 多 |
| 저가형 / 구형 키오스크 | ❌ 단일 언어 | 필요 | 화면 스캔으로 분석 |
| 무인 편의점형 | ⚠️ 상품 사진 중심 | 필요 | 텍스트 최소, 상품 인식 |

다국어 지원이 있더라도 번역 품질이 나쁘거나, 기능이 있는지 모르고 지나치는 경우도 많음.
실제 여행자가 키오스크 앞에서 막히는 상황은 충분히 발생함.

### 7.3 키오스크 특유의 기술 이슈

| 이슈 | 영향 | 대응 |
|---|---|---|
| 화면 반사 / 눈부심 | 이미지 품질 저하 | low_confidence 처리, 재촬영 유도 |
| 화면 밝기 | 색상 왜곡 | 클라이언트 전처리 (대비 보정) |
| UI 버튼 텍스트 혼재 | "주문하기", "Add to Cart" 등이 메뉴명으로 오인식 | 프롬프트 필터링 규칙 추가 |
| 상품 이미지 중심 구성 | 텍스트 없는 경우 | 이미지 기반 음식 인식 (Reverse Food Search 동일 플로우) |

### 7.4 프롬프트 추가 규칙

```
기존 프롬프트에 추가:
"이미지가 키오스크 화면인 경우:
 - '주문', '담기', '취소', '뒤로', 'Order', 'Add', 'Cancel', 'Back' 등
   UI 인터페이스 텍스트는 분석 대상에서 제외
 - 음식명, 가격, 음식 설명만 추출하여 분석
 - 상품 이미지가 주를 이루고 텍스트가 적은 경우
   이미지에 보이는 음식을 시각적으로 인식하여 분석"
```

### 7.5 개발 작업량

추가 개발 없음. 프롬프트 수정 + 기존 파이프라인 그대로 사용.
화면 반사 대응을 위한 이미지 전처리(대비 보정)는 MVP 이미지 리사이즈 로직에 포함 가능.

### 7.6 로드맵

| 단계 | 내용 |
|---|---|
| MVP | 키오스크 스캔 자연스럽게 동작 (별도 처리 없음) |
| V2 | 프롬프트에 UI 텍스트 필터링 규칙 명시 추가 |
| V2 | 화면 촬영 시 반사 감지 → "눈부심이 있어요. 각도를 조금 바꿔보세요" 안내 |

## 8. "음식 이름을 찍는다" — 전체 케이스 정의

서비스의 핵심 행위를 "메뉴판을 찍는다"에서 "음식 이름을 찍는다"로 넓혔을 때 발생하는 전체 케이스 정의.

### 8.1 케이스 분류표

| 케이스 | 분류 | 처리 방식 | 우선순위 |
|---|---|---|---|
| 일반 인쇄 메뉴판 | 핵심 | 기존 파이프라인 | MVP |
| 칠판 / 손글씨 메뉴 | 핵심 | low_confidence 처리 | MVP |
| 태블릿 / 화면 메뉴 | 핵심 | 기존 파이프라인 | MVP |
| 키오스크 화면 | 핵심 | UI 텍스트 필터 프롬프트 추가 | V2 |
| QR → 웹 메뉴 | 핵심 | jsQR → URL 파이프라인 | V2 |
| 개별 상품 라벨 (빵집/노점) | 핵심 | 다중 이미지 / 파노라마 | V2 |
| **호텔 룸서비스 메뉴** | **핵심 추가** | **가격 없는 메뉴판으로 처리** | **MVP** |
| **비행기 기내식 메뉴** | **핵심 추가** | **가격 없는 메뉴판으로 처리** | **MVP** |
| 음식 사진 (이름 모를 때) | 확장 | Reverse Food Search | V2 |
| 이미지 URL | 확장 | URL 파이프라인 | MVP |
| 텍스트 직접 입력 | 확장 | 텍스트 파이프라인 | MVP |
| 음식 광고판 / 현수막 | 확장 | 카메라/URL로 자연 처리 | 자동 커버 |
| 마트 델리코너 가격표 | 확장 | 자연 처리 가능 | 자동 커버 |
| 포장 식품 라벨 | 경계 | 안내 메시지 + 소프트 커버 | 후순위 |
| 편의점 상품 라벨 | 경계 | 안내 메시지 + 소프트 커버 | 후순위 |
| 영수증 (금액 분석) | 제외 | not_menu 처리 | 제외 |
| 식품 성분 상세 분석 | 제외 | 범위 외 안내 | 제외 |

### 8.2 호텔 룸서비스 / 기내식 처리

가격이 없거나 외화 단위가 낯선 경우가 많음. 기존 파이프라인 그대로 동작.
프롬프트에 아래 케이스 명시 추가:

```
가격이 없는 메뉴판 (호텔 룸서비스, 기내식 등):
  - 가격 필드 없어도 정상 처리
  - price: null 로 반환
  - category 필드로 appetizer / main / dessert / beverage 구분
  - 고급 호텔 메뉴 특성상 재료 설명이 길고 조리법 명칭이 복잡한 경우 多
    → Fun Fact 및 먹는법 설명 품질이 더 중요
```

### 8.3 포장 식품 / 편의점 소프트 커버

스캔 결과가 나오면 기존 음식 정보는 그대로 표시.
단, 결과 화면 상단에 컨텍스트 안내 메시지 추가:

```
"포장 식품이네요. 음식 기본 정보를 보여드려요.
 성분 상세 분석은 준비 중이에요."
```

판별 기준: Claude가 분석 결과에 `input_type: "packaged_food"` 필드 반환 시 표시.
프롬프트에 포장식품 감지 규칙 추가:

```
이미지가 포장 식품 라벨 (바코드, 영양성분표, 제조사 정보 포함)인 경우:
  input_type: "packaged_food" 반환
  음식명 번역 및 기본 재료는 정상 분석
  단, 영양성분 수치 분석은 하지 않음
```

## 10. 메뉴 옵션 / 커스터마이징 처리

### 10.1 케이스 분류

| 케이스 | 예시 | 처리 가능 여부 |
|---|---|---|
| 옵션이 메뉴판 이미지 내에 있음 | 서브웨이 빵 선택, 소스 선택 | ✅ Vision으로 파싱 |
| 옵션이 메뉴판 밖에 있음 | 전골 사리 추가, 구두 안내 | ⚠️ 대화 프리셋으로 커버 |
| 옵션 존재 여부 불명확 | 일반 식당 메뉴 | 감지 후 프리셋 제안 |

### 10.2 플로우

```
메뉴판 스캔
    │
    ▼
Claude Vision 분석
    │
    ├─ has_customization: true 감지
    │       ↓
    │   결과 카드에 옵션 표시
    │   + "추가 옵션 물어보기" → 대화 프리셋 직행
    │
    └─ has_customization: false
            ↓
        기존 결과 카드 (변화 없음)
```

### 10.3 JSON 스키마 추가

```typescript
interface DishAnalysis {
  // 기존 필드 유지
  has_customization: boolean

  options?: {
    label: string                    // "빵 선택", "소스", "사리 추가"
    type: 'single' | 'multi' | 'addon'
    required: boolean
    choices: {
      name: string                   // "Honey Oat"
      name_translated: string        // "허니 오트"
      price_delta?: number           // +1500, 0, null
      allergens?: string[]
    }[]
  }[]
}
```

옵션이 이미지에 있으면 파싱해서 채움.
이미지에 없지만 옵션 존재가 의심되면 `has_customization: true` + `options: []` 반환.

### 10.4 프롬프트 추가 규칙

```
옵션/커스터마이징 감지 규칙:
- 메뉴 항목 아래에 선택지 목록이 있으면 options 배열로 파싱
- "추가", "변경 가능", "선택", "Add-on", "Extra" 등의 키워드 감지 시
  has_customization: true 반환
- 옵션 가격이 명시된 경우 price_delta에 포함
- 이미지에 옵션 정보가 없어도 전골, 샤브샤브, 서브웨이 류의
  커스터마이징이 일반적인 음식 카테고리라면 has_customization: true 반환
```

### 10.5 결과 카드 UX

```
[부대찌개]  ₩12,000
  스팸, 소시지, 라면, 김치...
  ────────────────────────────
  사리 선택 가능              ← has_customization: true 시 표시
  [추가 옵션 물어보기  →]     ← 대화 프리셋 "추가 옵션" 카테고리로 직행
```

```
[Steak & Cheese]  $8.99
  스테이크, 치즈, 양파...
  ────────────────────────────
  빵 선택      Honey Oat / Wheat / Italian
  소스 선택    Mayo / Mustard / Chipotle   ← options 배열 렌더링
  추가         아보카도 +$1.50 / 베이컨 +$1.00
  [서버에게 주문 도움받기  →]
```

### 10.6 대화 프리셋 연동 — 추가 옵션 카테고리

기존 대화 프리셋 6개 카테고리에 옵션 관련 프리셋 보강:

```
주문 카테고리 추가 프리셋:
  "사리 추가할 수 있나요?"
  "소스를 바꿀 수 있나요?"
  "이거 빼고 만들 수 있나요?"
  "재료 추가 가능한가요?"
  "이거 빼달라고 할 수 있나요?"   ← 알러지 연동 가능

서버 예상 답변:
```

## 11. 알러지 대응 시스템 — 행동 도우미로 확장

### 11.1 설계 원칙

알러지 정보를 단순 표시하는 것에서 벗어나 실제 주문 행동까지 연결.
메뉴판 내 재료에서 알러지 프리셋이 감지되면 위험도를 4단계로 분류하고
각 단계에 맞는 UX 액션으로 연결.

### 11.2 4단계 위험도 분류

| 단계 | 코드 | 조건 | 예시 |
|---|---|---|---|
| 위험 | `main` | 알러지 재료가 메인 재료 | 해물탕의 새우·게 |
| 주의 | `sub` | 부재료, 제거 요청 가능 | 파스타 위 새우 토핑 |
| 확인 권장 | `possible` | 소스·육수·교차오염 가능성 | 새우젓, 해산물 육수 |
| 안전 | `none` | 해당 알러지 재료 없음 | — |

### 11.3 단계별 UX 액션

```
main (위험)
  → ❌ 뱃지 + "○○이 메인 재료예요" 경고
  → 같은 메뉴판 내 대안 메뉴 추천 팝업
  → 주문 자제 권고 (강한 어조)

sub (주의)
  → ⚠️ 뱃지 + "제거 요청 가능" 안내
  → 대화 프리셋 "○○ 빼고 만들 수 있나요?" 바로 연결

possible (확인 권장)
  → 〰️ 뱃지 + "확인 권장" 안내
  → 대화 프리셋 "○○ 들어가나요?" 연결

none (안전)
  → ✅ 조용히 표시 또는 생략 (화면 오염 최소화)
```

### 11.4 JSON 스키마 추가

```typescript
interface IngredientAllergenInfo {
  name: string
  allergens: string[]
  risk_level: 'main' | 'sub' | 'possible' | 'none'
}

interface AllergenSummary {
  preset_triggered: string[]      // 프리셋과 교차된 알러지 목록
  overall_risk: 'danger' | 'warning' | 'check' | 'safe'
  alternative_dishes?: string[]   // 같은 메뉴판 내 대안 메뉴명
}

interface DishAnalysis {
  // 기존 필드 유지
  ingredients: IngredientAllergenInfo[]
  allergen_summary: AllergenSummary
}
```

### 11.5 프롬프트 추가 규칙

```
알러지 위험도 판단 기준:
  main     — 해당 재료가 없으면 음식 자체가 성립되지 않는 경우
             (해물탕에서 해산물, 쉬림프 타코에서 새우)
  sub      — 해당 재료를 빼도 음식이 성립되는 경우
             (파스타 위 새우 토핑, 샐러드 위 견과류 등)
  possible — 소스, 육수, 조리 환경 등 명시되지 않은 경우
             (새우젓 사용 여부 불명, 공용 튀김 기름 등)
             식당마다 조리 방식이 다를 수 있으므로 possible로 처리

대안 메뉴 추천:
  - overall_risk가 danger인 경우에만 수행
  - 동일 스캔 결과 내 다른 메뉴 중 해당 알러지 없는 항목 필터
  - 카테고리 유사성 우선 (같은 찌개류, 같은 육류)
  - 최대 3개 반환
  - 외부 DB 조회 없음, 메뉴판 내에서만 추천
```

### 11.6 대화 프리셋 연결 문장

```
sub 케이스 자동 생성:
  "○○ 빼고 만들 수 있나요?"
  예: "새우 빼고 만들 수 있나요?"
      "견과류 빼고 주실 수 있나요?"

possible 케이스 자동 생성:
  "○○ 들어가나요?"
  예: "새우젓 들어가나요?"
      "해산물 육수 쓰나요?"
      "땅콩 기름 쓰나요?"

서버 예상 답변 (공통):
  [ 네, 들어가요 ]  [ 아니요, 없어요 ]  [ 확인해볼게요 ]
```

알러지 프리셋에 저장된 재료명을 기반으로 문장 자동 생성.
프리셋 설정 안 했을 경우 이 기능 미작동.

## 12. Fun Fact 톤 가이드

### 12.1 원칙

사실을 바꾸지 않되, 어디에 초점을 맞추는지를 제어.
음식을 경험하기 전 또는 경험 중에 보는 콘텐츠이므로 항상 식욕과 기대감을 높이는 방향으로.

### 12.2 피해야 할 프레임

```
❌ 빈곤 / 가난 / 싸구려 직접 언급
❌ "버려지는", "남은", "찌꺼기" 같은 부정적 재료 묘사
❌ 혐오감을 줄 수 있는 조리 과정 묘사 (내장, 발효 등)
❌ 전쟁, 기근, 궁핍함을 전면에 내세우는 서술
❌ "사실 이 음식은..." 식의 폭로 톤
❌ 음식의 가치를 낮추는 비교 ("저렴한 대용품으로 만든")
```

### 12.3 대신 이 방향으로

```
✅ 서민의 지혜    → "수백 년 된 조리법", "대를 이어온 레시피"
✅ 남은 재료 활용 → "제철 재료를 낭비 없이 쓰는 문화"
✅ 전쟁 중 탄생   → "극한 상황에서 피어난 창의성"
✅ 가난한 음식    → "대중의 사랑으로 살아남은 음식"
✅ 내장/특수부위  → "세계 각지의 미식가들이 주목하는 부위"
✅ 발효 음식      → "시간이 만들어낸 깊은 맛"
✅ 항상 마지막은 "지금 왜 이 음식이 맛있는가"로 마무리
```

### 12.4 문장 구조 공식

```
[흥미로운 역사/유래] + [긍정적 재프레이밍] + [지금 왜 맛있나]
```

### 12.5 케이스별 리라이팅 예시

| 음식 | 나쁜 버전 | 좋은 버전 |
|---|---|---|
| 빈대떡 | "빈자떡이라 불렸어요. 가난한 사람들이 먹던 음식이에요." | "조선시대부터 이어진 녹두 부침의 정석. 바삭한 식감의 비결은 녹두를 직접 갈아 쓰는 방식 그대로예요." |
| 부대찌개 | "미군 부대에서 나온 재료로 만들었어요." | "한국전쟁 이후 새로운 식재료를 창의적으로 받아들인 퓨전 감각. 지금은 K-푸드의 아이콘이에요." |
| 순대 | "돼지 창자에 당면을 채워 넣은 음식이에요." | "동물을 낭비 없이 쓰는 한국 전통 조리법의 정수. 쫄깃한 식감이 독특한 매력이에요." |
| 곱창 | "내장이라 꺼릴 수 있지만..." | "세계 미식 문화에서 내장 요리는 그 나라 식문화의 깊이를 보여줘요. 한국 곱창은 불 조절과 양념이 핵심이에요." |
| 홍어 | "발효시킨 홍어는 암모니아 냄새가 강해요." | "수백 년의 발효 역사를 가진 남도의 별미. 특유의 향과 쌉싸름한 맛은 한 번 경험하면 잊히지 않아요." |

### 12.6 Warning — Fun Fact와 별도 레이어로 유지

Fun Fact 톤은 식욕을 높이는 방향으로 조정하되,
Warning은 별도 레이어로 반드시 유지.
개인 호불호, 가게별 편차, 앱 분석의 한계를 명확히 안내해야
책임 소재가 앱으로 귀속되는 것을 방지.

Warning 표시 기준:

| 케이스 | 표시 조건 | 문구 방향 |
|---|---|---|
| 호불호 강한 음식 | 홍어·두리안·낫토·취두부 등 | "호불호가 갈릴 수 있어요. 처음이라면 소량 시도 권장" |
| 매운맛 편차 | spicy 점수 4 이상 | "가게마다 강도가 달라요. 미리 확인해보세요" |
| 발효 강도 편차 | 발효 음식 전반 | "숙성 정도에 따라 향과 맛이 크게 달라질 수 있어요" |
| 낯선 식감 | 내장류·특수 부위·생식 | "독특한 식감이에요. 취향에 따라 다르게 느껴질 수 있어요" |
| 알러지 possible | risk_level: possible | "이 재료가 사용될 수 있어요. 직접 확인해주세요" |

Warning 문구 원칙:
- "맛없다", "역하다" 같은 부정적 단언 금지
- 항상 "개인차", "가게마다 다름" 표현으로 불확실성 명시
- 앱 분석은 참고용임을 내포하는 표현 사용

### 12.7 앱 전체 면책 고지

현재 기획에 없는 항목. 추가 필요.

표시 위치:
- 온보딩 마지막 화면 1회
- 알러지 감지 결과 화면 항상 (배너 하단 작은 글씨)
- 결과 화면 최초 진입 시 1회 (이후 숨김)

문구:
```
분석 결과는 AI 기반 참고 정보예요.
실제 재료와 조리 방식은 가게마다 다를 수 있어요.
알러지가 있다면 반드시 직접 확인해주세요.
```

알러지 배너 하단 고정 문구 (더 짧게):
```
실제 조리 방식은 가게마다 달라요. 직접 확인을 권장해요.
```

### 12.8 프롬프트 추가 규칙

```
Fun Fact 작성 규칙:
  - 음식의 역사적 유래가 부정적(빈곤, 전쟁, 기근)이더라도
    그 사실을 "지혜", "창의성", "문화적 자산"으로 재프레이밍
  - 재료나 조리법이 낯설거나 혐오감을 줄 수 있는 경우
    혐오 요소 직접 묘사 없이 맛과 식감, 문화적 의미로 포커스 이동
  - 마지막 문장은 항상 현재 이 음식이 왜 맛있고 특별한지로 마무리
  - 금지 단어: 가난, 빈곤, 찌꺼기, 버려진, 싸구려, 냄새, 역겹
  - 권장 단어: 지혜, 전통, 장인, 정수, 깊은 맛, 특별한, 매력, 아이콘

  [성적 콘텐츠 금지 — 명시적 차단]
  - 정력, 성기능, 최음, 정력 강화, 성적 효능 관련 표현 일체 금지
  - "남성에게 좋다", "부부 관계에 도움", "스태미나" 등 성적 뉘앙스 금지
  - 민간 의학적 효능 주장 (과학적 근거 없는 건강 효과) 금지
  - 대신: 지역 특산물, 계절 보양식, 전통 문화, 영양 각도로 서술
  - 적용 사례:
      장어구이 → "복날 보양식", "단백질 풍부한 여름 음식" (정력 언급 금지)
      복분자주 → "지역 특산 과실주", "새콤달콤한 전통주" (정력 언급 금지)

Warning 별도 생성 규칙:
  - Fun Fact와 완전히 분리된 필드로 반환
  - warning_level: 'taste' | 'intensity' | 'texture' | 'alcohol' | null
  - warning_message: 간결하고 중립적인 1문장
  - 호불호 강한 음식 목록 (내부 기준):
    홍어, 두리안, 낫토, 취두부, 피단, 삭힌 홍어, 가오리찜,
    순대(내장), 곱창, 막창, 우거지, 청국장 등
  - 위 목록 해당 시 자동으로 warning_level: 'taste' 반환
  - 주류는 항상 warning_level: 'alcohol' 반환
```

### 12.9 fun_fact_detail — 접기 처리 (신규)

"사실이지만 첫인상에 식욕을 저하시킬 수 있는 내용"을 본문에서 분리해
사용자가 선택적으로 열어볼 수 있는 접기 필드로 제공.

적용 대상:
- 어원이 부정적인 경우 (ホルモン "버리는 것", 빈대떡 "빈자떡")
- 유래가 충격적일 수 있는 경우 (부대찌개 미군 부대 재료)
- 재료 상세가 식욕 저하를 유발할 수 있는 경우 (순대 창자, 곱창 내장)

```json
{
  "fun_fact": "일본 야키니쿠 마니아들이 찾는 부위예요...",
  "fun_fact_detail": {
    "label": "이름의 유래가 궁금하다면",
    "content": "호루몬은 두 가지 어원설이 있어요. 독일어 Hormon(호르몬)에서 왔다는 설과, 관서 방언 호루몬(버리는 것)에서 왔다는 설이 공존해요. 어느 쪽이 맞든 지금은 야키니쿠의 핵심 메뉴예요."
  },
  "warning": {
    "level": "texture",
    "message": "내장 특유의 식감과 향이 있어요. 부위에 따라 맛이 크게 달라요."
  }
}
```

fun_fact_detail이 없으면 null 반환.

UX: 기본 닫힘, 탭하면 펼쳐짐. 레이블은 "▶ [label]" 형태.
라벨 예시:
  "이름의 유래가 궁금하다면"
  "탄생 배경이 궁금하다면"
  "재료에 대해 더 알고 싶다면"

### 12.10 사용자 문화권 기반 Disclosure — 필터링이 아닌 맥락 강화

#### 설계 원칙

output_language는 콘텐츠를 필터링하는 게 아니라
사용자 문화권에 맞게 disclosure 강도와 맥락을 조정하는 신호.
여행 앱의 목적은 다른 문화를 알아가는 것 — 콘텐츠 자체는 유지.

```
필터링 (X)   한국인이라서 "보양식" 언급 차단
맥락 강화 (O) 한국인이라서 보양식·정력 연상 가능성 → disclosure에 경고 강화
```

#### disclosure 필드

warning(음식 자체 특성)과 분리된 별도 필드.
문화권 간 간극이 클 때만 생성. 모든 음식에 생성하지 않음.

```json
{
  "fun_fact": "...",
  "fun_fact_detail": { "label": "...", "content": "..." },
  "warning": { "level": "taste", "message": "..." },
  "disclosure": {
    "target_culture": "ko",
    "message": "한국의 곱창과 유사한 부위예요. 일본식 조리는 소금·된장 베이스로 달라요."
  }
}
```

disclosure가 없으면 null 반환.

#### 언어별 disclosure 강도 조정 방식

| 상황 | 대상 | disclosure 방향 |
|---|---|---|
| 한국인 → ホルモン | ko | 한국 곱창·막창과 연결해 친숙한 맥락 제공 |
| 한국인 → 복분자주 | ko | 보양주 연상 → "과음 주의" 경고 강화 |
| 서양인 → 홍어삼합 | en | 블루치즈 발효와 유사 맥락으로 설명 + 경고 강화 |
| 서양인 → 내장 요리 | en | 익숙한 비유 + 문화적 의미 설명 추가 |
| 아랍권 → 복분자주 | ar | 알코올 경고 더 강하게 disclosure에 표기 |
| 일본인 → 낫토 | ja | 익숙한 음식이므로 disclosure 불필요 → null |

#### 프롬프트 지시 방식

별도 필터링 로직 없음. 프롬프트 컨텍스트로 전달하면 Claude가 조정.

```
User context:
  output_language: "ko"
  dietary_beliefs: []

Disclosure 생성 규칙:
  - 사용자 문화권(output_language)과 음식 문화권(menu_language) 간
    맥락 간극이 클 때만 disclosure 생성
  - 필터링 금지 — 콘텐츠 자체는 항상 유지
  - 한국어 사용자: 한국 문화에서 민감하게 연상될 수 있는 포인트
    (보양식·정력 연상 가능성)는 disclosure에 경고로 표기
  - 영어 사용자: 낯선 문화 음식은 익숙한 비유로 맥락 제공
  - 아랍어 사용자: 주류·돼지고기 관련 disclosure 강화
  - 현지인과 동일 문화권이면 disclosure 생략
```

#### 케이스별 예시

```
한국인 / ホルモン (일본 내장 요리)
  disclosure: "한국의 곱창·막창과 유사한 부위예요.
               일본식은 소금·된장 베이스 양념이 일반적이에요."
  → 익숙한 것에서 출발해 차이점 안내

서양인 / 홍어삼합 (한국 발효 홍어)
  disclosure: "발효 향의 강도가 블루치즈보다 강할 수 있어요.
               첫 경험이라면 소량부터 권장해요."
  → 익숙한 것에 빗대어 강도 감각 제공

한국인 / 복분자주
  disclosure: "한국에서 보양주로 알려진 만큼
               과음 시 다음날 컨디션에 주의하세요."
  → 한국 문화 맥락 아는 사람에게 실용 경고 강화

아랍권 / 복분자주
  disclosure: "알코올이 포함된 주류예요.
               할랄 식이 기준에 해당하지 않아요."
  → dietary_beliefs 설정 여부와 무관하게 강하게 표기
```

### 12.11 성적 콘텐츠 vs 문화/유머 콘텐츠 — 판단 기준

유사해 보이지만 다르게 처리해야 하는 케이스.

| 케이스 | 분류 | 처리 |
|---|---|---|
| "장어는 정력에 좋다" | 성적 콘텐츠 | 완전 금지, 대체 프레임 |
| "복분자는 남성 활력에 좋다" | 성적 콘텐츠 | 완전 금지 |
| "요강이 뒤집힌다는 전설" | 문화/유머 | fun_fact_detail 접기 허용 |
| "신장·배뇨 기능에 좋다는 민간 기록" | 전통 의학 | fun_fact_detail 접기 허용 |

판단 기준:
- 성적 기능(발기, 정력, 최음)을 직접·간접 언급 → 금지
- 신체 기능(소화, 배뇨, 혈액순환)을 문화·유머 맥락에서 언급 → 접기 허용
- 민간 전설, 이름 유래, 역사적 사용 기록 → 접기 허용

복분자주 적용 예시:
```json
{
  "fun_fact": "전북 고창 특산 복분자로 빚은 새콤달콤한 과실주예요. 짙은 루비색과 풍부한 안토시아닌이 인상적이에요.",
  "fun_fact_detail": {
    "label": "이름의 유래가 재밌어요",
    "content": "복분자(覆盆子)는 항아리를 뒤집는다는 뜻이에요. 마시면 기운이 넘쳐서 요강이 뒤집힌다는 옛 선조들의 재치 있는 표현에서 유래했어요."
  }
}
```

금지 예시 (같은 음식이지만):
```
"복분자는 예로부터 정력 강화에 좋다고 알려져 있어요" → 완전 삭제
"남성 스태미나 음식으로 유명해요" → 완전 삭제
```
