## 1. 시장 검증 부재

### 1.1 TAM이 없다

"여행자" "언어 장벽" "알러지"를 타겟이라고 했는데
실제로 Transtaste가 먹을 수 있는 파이 계산이 없다.

```
필요한 숫자 (현재 전무):
  연간 해외여행자 중 메뉴 언어 장벽을 심각하게 느끼는 비율
  그 중 앱으로 해결하려는 비율
  그 중 유료 전환 의향이 있는 비율
  그 중 Transtaste를 선택할 이유가 있는 비율

"여행 앱 시장 $650B" 류의 거대 시장 수치는 의미 없음
Transtaste가 실제로 접근 가능한 SAM/SOM이 필요
```

### 1.2 핵심 가정이 하나도 검증되지 않았다

| 가정 | 현실 | 검증 여부 |
|---|---|---|
| 메뉴 언어 장벽이 충분히 큰 페인포인트 | Google Lens가 이미 무료 제공 | ❌ |
| 알러지 여행자가 앱으로 해결하려 한다 | Equal Eats 카드를 이미 갖고 다님 | ❌ |
| Fun Fact / 먹는 방법이 유료 전환을 만든다 | 재밌고 닫을 가능성도 높음 | ❌ |
| 서버가 보여주기 화면을 이해하고 협력한다 | 현지 식당 직원 반응 미지수 | ❌ |
| 캐시 히트율 60%+ 달성 가능 | 메뉴판은 다양해서 초기 히트율 낮을 수 있음 | ❌ |

## 2. 수익 모델 구조적 약점

### 2.1 LTV가 낮다

```
여행자 = 구조적 1회성 고객

최대 LTV 시나리오:
  Trip Pass 7일  $2.99
  Trip Pass 30일 $5.99
  연 2회 여행    최대 $11.98/년

이 LTV로 CAC(유저 획득 비용)을 감당할 수 있는가?
앱스토어 광고, 인플루언서, 콘텐츠 비용이 $11.98보다 낮아야 함
현실적으로 어렵다
```

### 2.2 캐싱 역설

```
캐시 히트율 상승 → 사용자 무료 혜택 증가
                  → 유료 전환 압력 감소

즉 서비스가 잘 될수록 수익화가 어려워지는 구조가 될 수 있음
"캐싱이 수익률을 극대화한다"는 반은 맞고 반은 틀림
비용은 줄지만 전환율도 같이 줄 수 있음
```

### 2.3 Free 10회 전환 타이밍 불확실

```
여행 첫날 소진 → Trip Pass 구매 자연스러움 ✅
여행 마지막날 소진 → 이미 집에 가는 시점 → 전환 없음 ❌

소진 타이밍을 제어할 수단이 현재 없음
```

### 2.4 대체재가 무료로 충분히 존재

```
Google Lens    무료, 즉시 사용 가능
ChatGPT App    카메라 기능 + 번역 가능
네이버 파파고   한국인에겐 익숙하고 무료

"굳이 유료로?" 순간이 안 올 수 있음
차별점이 유료 전환 드라이버로 충분한지 검증 안 됨
```

```
                앱스토어 생태계 장악력

이 중 하나라도 움직이면 Transtaste의 핵심 차별점 즉시 위협
```

## 4. 사용자 행동 가정 검증 안 됨

### 4.1 실제 식당에서 앱을 켜는가

```
여행 중 식당 도착 → 앉자마자 메뉴판 나옴
→ 배고프고 대화 중이고 분위기 즐기고 싶음
→ 앱 켜서 사진 찍고 기다리는 UX가 자연스러운가?

현실: 대부분 그냥 눈치껏 주문하거나 구글 번역으로 몇 단어만 확인
Transtaste를 꺼내는 모멘트가 실제로 발생하는지 검증 없음
```

### 4.2 알러지 사용자는 이미 준비돼 있다

```
심각한 알러지 보유자:
  → Equal Eats 카드 이미 갖고 다님
  → 여행 전 식당 리서치 철저히 함
  → Transtaste 스캔보다 사전 확인을 더 신뢰

가벼운 알러지 보유자:
  → 이미 알고 있어서 눈으로 재료 확인
  → 앱까지 쓰는 마찰이 있음

Transtaste 알러지 기능이 실제로 가장 필요한 사람이 누구인지 불명확
```

### 4.3 서버에게 보여주기가 실제로 작동하는가

```
가정: 서버가 화면을 보고 협력해준다
현실:
  고급 식당  → 서버가 영어 가능하거나 사진 메뉴 제공
  로컬 식당  → 화면 보는 UX 낯설 수 있음
  바쁜 시간대 → 서버가 화면 들여다볼 여유 없음

실제 사용 환경 테스트 없음
```

## 5. 인디 개발자 실행 가능성

현재 기획에 포함된 작업량 전체:

```
개발 영역:
  Next.js + Supabase + Redis + Stripe + Claude API 통합
  PWA + 스트리밍 + 2단계 lazy-load
  주문서 + 전체화면 Present Mode + wake lock API
  알러지 4단계 시스템 + 대화 프리셋 + 팁 문화 자동화
  QR 코드 스캔 + 이미지 URL 처리 + 텍스트 입력

콘텐츠 영역:
  대화 프리셋 번역 (6개국어 × 30+ 문장 = 180+ 항목)
  팁 문화 데이터 20개국 수작업
  알러지 표준 데이터 14종 + 식이 신념 6종
  음식별 SEO 페이지 50개+
  FAQ Schema 마크업

마케팅 영역:
  Reddit 커뮤니티 운영
  여행 블로거 협업
  앱스토어 최적화 (다국어)
  llms.txt 작성
```

**이 중 MVP 범위가 얼마인지 명확하지 않다.**
"기획은 완벽한데 출시 못한 앱"이 가장 나쁜 결과.
MVP 스코프를 반으로 줄이고 실제로 출시하는 것이 전략적으로 옳다.

## 6. 법적 리스크 — 현재 문서에 단 한 줄도 없음

### 6.1 AI 알러지 정보 제공의 제품 책임

2025년 기준 AI 서비스에 대한 제품 책임 소송이 현실화됐다.

<핵심 판례>
Shamblin v. OpenAI (2025년 11월, 캘리포니아):
AI 출력물을 "제품"으로 보고 제품 결함 및 경고 실패 이론 적용.
법원이 First Amendment 방어 논리를 기각하고 소송 진행 허용.

Character.AI 자살 소송 (2025년 5월 플로리다):
연방 판사가 기각 신청 거부 → AI 출력물 = 제품 책임 적용 가능 선례.

```
Transtaste 리스크 시나리오:
  사용자 A: 새우 알러지 있음
  Transtaste: "possible" 표시 (확인 권장)
  사용자 A: 확인 안 하고 먹음 → 아나필락시스 → 입원

  질문: Transtaste가 "참고용"이라고 명시했어도 책임에서 자유로운가?
  현실: 면책 조항이 모든 책임을 막지 못한다 (특히 미국)
```

### 6.2 FDA FALCPA / FASTER Act

FDA의 9대 주요 알러지 목록: 우유, 달걀, 생선, 갑각류, 견과류, 땅콩, 밀, 대두, 참깨 (2021년 FASTER Act로 참깨 추가).

Transtaste는 식품 제조사가 아니므로 FALCPA 직접 적용 대상은 아니다.
하지만 알러지 정보를 제공하는 서비스로서 정보 정확성에 대한 책임 논란 가능.

```
리스크:
  Transtaste가 제공한 알러지 정보가 틀렸을 때
  사용자가 그 정보를 믿고 행동했을 때
  피해가 발생했을 때

면책 조항이 있어도:
  미국에서 배심원은 면책 조항보다 실제 피해에 반응
  "AI가 틀렸다 → 앱 개발자 책임"으로 가는 법리 형성 중
```

### 6.3 GDPR — 알러지 데이터는 건강 정보

```
EU 사용자 알러지 프리셋 저장 = 건강 관련 민감 정보
GDPR Article 9: 특별 범주 데이터 (건강 정보) 처리 규정

요구사항:
  명시적 동의 (Explicit Consent) — 체크박스 하나로 부족
  목적 제한 (Purpose Limitation) — 알러지 데이터를 마케팅에 쓰면 위반
  데이터 최소화 (Data Minimization) — 필요 이상 수집 금지
  삭제권 (Right to Erasure) — 요청 시 완전 삭제 보장

위반 시: 연 매출 4% 또는 €2,000만 중 높은 금액
스타트업이 GDPR 위반으로 폐업하는 사례 다수
```

### 6.4 한국 개인정보보호법

```
한국 사용자 대상 서비스 → 개인정보보호법 적용
알러지 정보 = 건강 정보 = 민감정보

요구사항:
  민감정보 처리 동의 별도 취득 필수
```

### 6.5 앱스토어 정책 리스크

```
Apple App Store:

  → 의료 기기로 분류될 경우 FDA 허가 필요 (극단적 시나리오)
```

### 6.6 최소 법적 보호 장치

지금 당장 필요한 것 (비용 최소):

```
1. 이용약관 (Terms of Service)

4. 변호사 리뷰
   - 출시 전 약관 전문 변호사 검토 (1회성, 비용 가능)
   - 미국 서비스 타겟 시 미국법 기준 면책 조항 필수
```

## 7. 추가로 놓친 시각들

### 7.1 사용자 신뢰 형성 문제

```
Transtaste는 신규 앱이다.
알러지 같은 건강 관련 정보에서 사용자는 신뢰를 먼저 요구한다.

질문: 아무도 모르는 앱의 알러지 정보를 믿을 것인가?

신뢰 형성 없이 출시하면:
  → 무료 사용자는 쓸 수 있음
  → 유료 전환 시 "이 앱 믿을 수 있나?" 질문 발생
  → 알러지 심한 사람일수록 전환 저항 높음 (역설)
```

### 7.2 문화권별 앱 사용 행태 차이

```
Transtaste가 타겟하는 여행자 = 다국적

한국인    앱 설치 허들 낮음, 새로운 앱 시도 적극적
일본인    이미 익숙한 앱 쓰는 경향, 신규 앱 진입 장벽 높음
서양인    앱 대신 구글 번역 습관화
고령 여행자 스마트폰 앱 마찰 큼

"여행자"를 단일 타겟으로 보면 안 됨
초기 타겟 사용자층을 좁혀야 마케팅 집중 가능
```

### 7.3 오프라인 사용 시나리오 미검토

```
해외 로컬 식당 = 와이파이 없음
데이터 로밍 = 느리거나 없음

현재 Transtaste = 100% 온라인 의존
→ 정작 가장 필요한 순간 (오지, 로컬 맛집)에 작동 안 할 수 있음

경쟁앱 일부는 오프라인 지원을 차별점으로 내세움
히스토리 오프라인 저장이라도 지원 여부 검토 필요
```

### 7.4 앱 품질 인식 문제

```
MVP로 출시하면 초기 품질이 낮을 수 있음

여행 중 처음 쓰는 앱이 오작동하면:
  → 재설치 안 함
  → 나쁜 리뷰 → 앱스토어 평점 하락
  → GEO 전략에도 악영향 (신뢰도 신호)

"여행 중 처음 쓰는 앱" = 두 번의 기회가 없는 시장
MVP 품질 기준을 높게 잡아야 함
```

### 7.5 수익화 타이밍이 너무 이름

```
앱 인지도 0인 상태에서
Free 10회 제한 + 유료 전환 = 사용자 이탈 가능

초기 성장 단계에선 무제한 무료 → 리텐션/입소문 먼저
일정 MAU 확보 후 유료 전환 도입이 더 나을 수 있음

단, 이 전략은 서버/API 비용이 발목을 잡음
비용 구조 때문에 처음부터 유료화를 해야 한다면
Free 10회가 충분한 체험을 제공하는지 재검토 필요
```

### 7.6 한국어 중심 기획의 글로벌화 문제

```
현재 기획 = 한국인 여행자 관점에서 작성됨

글로벌 출시 시:
  영어권 사용자 → 번역 방향이 다름 (영어 → 현지어)

```

## 11. 감사 지적사항 대응 매핑

> 단순 반론이 아니라 실증 근거 + 실제 개선 가능 항목까지 정리.

---

### 11.1 "메뉴 언어 장벽이 충분히 큰 페인포인트인가? Google Lens가 있는데"

**대응 — 실증 반론**

Google Lens / Google Translate는 이미 존재하는데도 실패가 계속 발생한다.

| 언어쌍 | 원문 | 기계번역 결과 | 실제 의미 |
|---|---|---|---|
| 중국어→한국어 | 涼拌苦菊 | 서부 아프리카 원주민의 쓰라린 추위 | 쓴 채소 냉채 |
| 한국어→영어 | 김치찜 | Kimchi wishlist | 김치를 쪄서 조린 요리 |
| 스페인어→영어 | Sepia a la plancha con alioli | Sepia to the iron with ali smelt | 갑오징어 그릴 + 마늘 마요네즈 |
| 프랑스어→영어 | langue de boeuf | baked language | 소 혀 요리 |
| 폴란드어→불가리아어 | Szyjki rakowe | 자궁경부암 | 가재 꼬리 요리 |

문제가 해결 안 됐다는 실증 증거. Google Lens는 번역 도구고 Transtaste는 해석 도구, 카테고리가 다르다.

**실제 개선 — 이 사례들을 앱 내 활용**

```
온보딩 슬라이드:
  "Google Translate로는 이렇게 나와요" → "Transtaste는 이렇게 나와요"
  비포/애프터 비교 슬라이드로 차별점 즉시 전달

앱스토어 스크린샷:
  기계번역 실패 사례 이미지 → Transtaste 결과 카드 비교
  심사 통과 가능한 형태로 구성

GEO 콘텐츠:
  음식별 페이지에 "Google Translate로 검색하면 이렇게 나옵니다" 섹션 추가
  → "kimchi wishlist meaning", "sepia a la plancha english" 류 검색 유입
```

---

### 11.2 "알러지 심한 사람은 Equal Eats 카드 이미 갖고 다님"

**대응 — 포지션 차별화**

Equal Eats = 사전 준비된 고정 선언 카드
Transtaste = 현장 메뉴판 기반 즉시 대응

```
Equal Eats  "저는 새우 알러지가 있어요" (고정, 메뉴와 무관)
Transtaste  "이 메뉴판에서 새우 있는 음식: 해물탕, 새우볶음밥
             대안: 된장찌개 ✅, 불고기 덮밥 ✅
             물어볼 문장: '새우 빼고 만들 수 있나요?'"
```

Equal Eats가 존재한다는 사실 자체가 알러지 여행자 시장이 실재한다는 증거.
두 서비스는 경쟁이 아니라 보완 관계.

**실제 개선 — 알러지 사용자 온보딩 강화**

```
온보딩에 알러지 카드 즉시 생성 기능 추가:
  프리셋 설정 완료 → "이 카드를 저장해두세요"
  → 오프라인에서도 보여줄 수 있는 알러지 카드 자동 생성
  → Equal Eats 사용자도 Transtaste로 마이그레이션 가능

마케팅 포인트:
  "카드 따로, 앱 따로 필요 없어요"
```

### 11.3 "Google이 내일 메뉴 알러지 기능 추가하면?"

**대응 — 부분 인정 + 구조적 방어선**

인정: 실제 위협이고 부정할 수 없다.

반론:
```
Google Translate 카메라 기능은 이미 5년 이상 존재
→ 여전히 "Sepia to the iron"이 나옴
→ 플랫폼이 음식 도메인에 집중 투자를 안 한다는 방증

Google이 가져갈 수 없는 것:
  hit_count 기반 실사용 음식 데이터
  알러지 4단계 UX 레이어
  식당 대화 프리셋 + 서버에게 보여주기 플로우
  "식당 컴패니언" 단일 포지션
```

**실제 개선 — 방어선 강화**

```
데이터 해자 구축:
  사용자가 많아질수록 hit_count 데이터가 쌓임
  → 인기 음식 정확도 지속 개선
  → Google이 복제하기 어려운 실사용 데이터셋

음식별 콘텐츠 페이지 조기 구축:
  출시 전 50개 → 3개월 후 200개 → 6개월 후 500개
  → AI 인용 소스로 자리잡을수록 대체 어려워짐
```

### 11.4 "LTV $11.98로 CAC를 감당할 수 있는가"

**대응 — CAC 구조 전환**

전통적 CAC 공식이 적용 안 되는 구조.

```
GEO 전략 실현 시:
  음식 이름 검색 → AI가 Transtaste 언급 → 유입
  CAC = $0

Earned Media 실현 시:
  "Kimchi wishlist" 밈 → 소셜 바이럴 → 유입
  CAC = $0

여행자 커뮤니티 특성:
  정보 공유 매우 활발
  한 명이 추천하면 같은 여행지 가는 지인에게 전파
  → 바이럴 계수(K-factor)가 일반 앱보다 높음
```

**실제 개선 — CAC 낮추는 구조**

```
추천인 시스템:
  "친구에게 공유하면 크레딧 +5회"
  → 여행 동행자 그룹 내 자연 전파

여행 커뮤니티 타겟 Earned Media:
  Reddit r/JapanTravel, r/solotravel
  "이 앱 써봤는데..." 형태의 자연스러운 언급 유도
  → 광고비 없이 신뢰도 높은 유입
```

### 11.5 "초기 타겟을 한국인 여행자로 좁혀야 한다"

**대응 — TAM 재정의**

새 리서치 결과: 서양권끼리도 동일 문제 발생.

```
기존 가정:  한국인 → 아시아 여행 (좁은 TAM)
새 발견:    유럽인 → 유럽 식당, 미국인 → 스페인/프랑스 여행도 동일 문제

포지션 확장:
  "아시아 메뉴판 전용 앱"
  → "언어 장벽이 있는 모든 식당 여행자"
```

**실제 개선 — 글로벌 타겟 단계적 확장**

```
1단계 (MVP):      한국어 UI, 한국인 여행자, 아시아 메뉴판 집중
2단계 (V2):       영어 UI 추가, 영어권 여행자 유입
3단계 (V3):       일본어/스페인어 UI, 로컬 시장 진입

단계별로 잡아도 충분
오히려 한국인 집중이 MVP 범위를 현실화하는 장점
```

```
현재 상태: 현장 테스트 없음, 가장 취약한 지점

실제 개선:
  베타 테스트를 실제 식당에서 진행
  → 다양한 식당 유형별 서버 반응 기록
  → "고급 식당 / 로컬 식당 / 패스트푸드" 시나리오 분류

Present Mode UX 개선 포인트:
  글씨 크기: 현재 계획보다 더 크게 (32px → 40px 이상)
  화면 배경: 무조건 흰색 (서버 가독성 최우선)
  메뉴명: 원문 + 번역 둘 다 표시 (서버가 자기네 메뉴 확인 가능)
  확인 버튼: "확認しました" 현지어로 크게
```

### 11.7 "인디 혼자 감당 가능한가"

**대응 — MVP 스코프 재정의**

```
현재 기획 전체 = V3까지의 합산
실제 MVP = 훨씬 작아야 함
```

**재평가 — Claude API가 공수 구조를 바꾼다**

```
일반 인디 개발자 기준 우려 항목들이
Claude 프롬프트 + JSON 스키마로 대체된다:

  알러지 4단계 시스템        → 프롬프트 규칙
  대화 프리셋 현지어 생성    → 로컬 JSON 번들
  Fun Fact 조건부 생성       → 프롬프트 규칙
  disclosure 문화권 맥락     → output_language 컨텍스트
  대안 메뉴 추천             → 동일 스캔 내 필터링
  브랜드명 분리              → 프롬프트 규칙
  시즌 메뉴 감지             → 프롬프트 규칙

실제 개발 공수가 남는 것:
  Next.js 라우팅 + 컴포넌트
  Supabase 스키마 + Auth
  Stripe 결제 플로우
  Redis 캐싱 레이어
  스트리밍 SSE 파이프라인
  기본 대화 프리셋 JSON 데이터

→ Claude 없이도 인디가 3개월이면 치는 범위
→ Claude가 들어가면 기능 밀도 대비 코드량이 극단적으로 작아짐
→ MVP 스코프 우려는 일반 인디 개발자 기준이었음, 재평가 필요
```

**실측 데이터 (2026-03-28 기준)**

```
Claude Code 활용 시 개발 속도 실측:
  일반 개발자 기준 1개월 작업 = Claude Code 하루
  일반 개발자 기준 1~2개월 작업 = Claude Code 프롬프트 5회 수준

즉:
  현재 기획 전체 = 일반 인디 기준 6~12개월
  Claude Code 활용 시 = 실질 2~4주 수준으로 압축 가능

이 수치는:
  "인디 혼자 감당 가능한가" 감사 지적의 완전한 반론
  "Google이 따라하기 어렵다"는 방어선 논거 강화
  (대기업은 Claude Code 방식으로 개발하지 않음)
```

MVP 범위 그대로 유지. 실행 속도가 우려 대상이 아님.

### 11.8 미결 — 여전히 약한 부분
